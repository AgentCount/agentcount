# ERC-8004 conformance census — Base, 2026-07-28

Run `1c87c4f4-c4c4-45ee-b03a-d8517f4d5d8a`. This is the first published report
from Ledgerscope. It states what was measured, the ladder result for this run,
what each rung's failures consist of, the caveats that apply to reading it,
and how to reproduce every number in it. Nothing here is a score. See
[`METHODOLOGY.md`](../../METHODOLOGY.md) for the rules behind every rung
referenced below; this report only applies them to one run's data.

## 1. What was measured

Every agent id registered in the ERC-8004 Identity Registry on Base, as of
block **49,230,618**, was read through as much of the seven-rung ladder as
the current implementation supports (rungs 1–5 and 7; rung 6 is not
implemented — see §3 and §4). Each agent's on-chain state (owner, token URI)
was read once, at that single pinned block, so the population this run
describes existed simultaneously — not assembled from reads taken minutes
apart. The off-chain document each agent points at was then fetched once and
evaluated; reputation-registry reads (rung 7) were likewise taken from the
same pinned block.

- **Chain:** Base (`chain_id` 8453), Identity Registry
  `0x8004a169fb4a3325136eb29fa0ceb6d2e539a432`.
- **Pinned block:** 49,230,618.
- **`checker_commit`:** `6ffb9da8a03063051fe7253d70bcfdd2432b8cd7`.
- **`spec_commit`:** `68fc6765761a10fb26f0692df21c8a6f9d12b1be`.
- **Agent ids discovered:** 60,061. **Read and persisted:** 60,049.
  **Unreadable:** 12 — an RPC failure on our side prevented reading these 12
  agents at all. They carry no rows in this run and are excluded from every

All figures below were queried directly against `check_results` and

**817 of 60,049 agents (1.4%) clear every rung this run measured.** That
figure is rung 7's pass count directly — rung 7 only ever runs for an agent
that already passed rung 5 (1,437 agents reached it; 817 of those passed),
so "passed rung 7" and "passed every implemented rung" are the same claim
for this run.

A note on how the skip counts read across rungs, because the row counts in
the table above do not all share the same denominator. `skipped` rows carry
`skipped_because_rung`, naming the rung that actually stopped the agent —
not necessarily the row immediately below. For the overwhelming majority of
the 28,181 agents stopped at rung 2 (27,928 of them), the only row written
above rung 2 is the single `skipped` row at rung 3; no rung-4 or rung-5 row
exists for them at all (absent, not `skipped`, not `fail`). A smaller,
exact set of 253 agents — the same 253 identified in §3's rung-4 and rung-5
"skipped-forward" figures — additionally carry a `skipped` row at rung 4
*and* rung 5, both still citing rung 2 as the stopping point. Both patterns
are legitimate under the rule in `METHODOLOGY.md` §4 (an absent rung is
never a failure claim); this run's sweeper evidently does not write a
`skipped` row for every rung above a stop in every case, and this report
states the observed split rather than asserting a single rule that the data
does not support. Once an agent has not passed rung 5, it has no rung 7 row
at all (not even `skipped`) — rung 6 sitting unimplemented between them
means the ladder simply stops emitting rows rather than fabricating a
`skipped` verdict for a rung with no code behind it. 58,612 agents (60,049
− 1,437) therefore have no rung 7 row of any kind; that absence is not a
rung-7 failure, it is rung 5 or earlier having already stopped the ladder.

## 3. What each rung's failures consist of

**Rung 2 (`resolvable`), 25,495 `fail` + 2,686 `error`.** Fail breaks down
by evidence `reason`:

| Reason | Count |
|---|---:|
| `no_uri` (empty `tokenURI()`) | 19,750 |
| `http_status` (non-2xx response) | 4,192 |
| `unsupported_scheme` | 1,035 |
| `payment_required` (HTTP 402) | 105 |
| `ssrf_blocked: resolves to a non-public address` | 267 |
| `ssrf_blocked: dns resolution failed` | 145 |
| `ssrf_blocked: non-public address` | 1 |

The 2,686 `error` results are ours, not the agent's: 2,177 are
`robots_disallowed` (the origin's own `robots.txt` refused our fetch — a
consequence of us honoring it, not of anything the agent published), 362
are our own request timeouts, 143 are `robots_unavailable` (we could not
retrieve `robots.txt` itself to know whether we were allowed to proceed),
and 4 are connection failures on our side.

**Rung 3 (`parseable`), 2,046 `fail`.** These are the 31,868 rung-2 passes
minus the 29,811 that parsed and the 11 that errored on our side — bodies
that were fetched successfully but did not decode as JSON (truncated
responses, HTML error pages served with a 200 status, binary payloads).

**Rung 4 (`conformant`), 25,636 `fail` out of 30,064 attempts (4,175 pass +
253 skipped-forward from an earlier stop).** Missing-field frequency across
every failing document (a document can be missing more than one field, so
these do not sum to 25,636):

| Missing field | Documents missing it |
|---|---:|
| `x402Support` | 20,897 |
| `type` | 15,808 |
| `services` | 13,645 |
| `active` | 13,081 |
| `image` | 12,458 |
| `registrations[].agentId` (conditional) | 209 |
| `description` | 72 |
| `registrations[].agentRegistry` (conditional) | 133 |
| `name` | 20 |

**`x402Support` is the only field missing from 6,269 of the 25,636 rung-4
failures** — 24.5% of all conformant-check failures are a document that has
every other required field and is missing exactly this one. This is a
spec-versus-practice gap, reported as arithmetic: 6,269 documents that would
pass rung 4 today if this one field were present, do not. We have not
established *why* — the obvious hypothesis is that the tooling used to
generate these documents predates `x402Support` being added to the required
set, or does not emit it, but that hypothesis is untested against any
document-generation-tooling data we do not have.

**Rung 5 (`bound`), 2,738 `fail` out of 30,064 attempts (1,437 pass + 25,889
skipped-forward).** Two distinct failure shapes, and they are not the same
claim:

- **2,182 documents (79.7% of rung-5 fails) declare no `registrations` entry
  at all** — evidence `reason: "no_registrations"`. A document with no
  registrations array is not itself a rung-4 failure (Ruling 2 in
  `METHODOLOGY.md` §2 makes the array's presence optional), but it cannot
  satisfy rung 5's question of whether the document names the record it was
  fetched from, because it names no record at all.
- **556 documents (20.3%) declare a registration that does not match** the
  chain, registry address, or token id this fetch actually originated from —
  evidence `match: false` with a populated `declared_chain` /
  `declared_registry` / `declared_agent_id` that disagrees with what this
  run fetched from.

**Rung 6 (`live`) produced no rows.** It is specified in `METHODOLOGY.md`
§2 but not implemented; no agent in this run has a rung-6 verdict of any
kind, and none should be inferred.

**Rung 7 (`independent`), 620 `fail`, 0 `skipped`, 0 `error`, out of 1,437
attempts.** All 620 failures carry `reason: "no_feedback"` —
`distinct_authors: 0` for every one of them. **Zero agents in this run
failed with `reason: "only_self_feedback"`.** This distinction exists in
the check specifically to separate "nobody showed up" from "the owner
showed up and nobody else did," and this run's data lands entirely in the
first category: no chain read in this run found an agent whose only
feedback author was its own owner. This is reported only because the check
distinguishes the two cases and both are visible in the data — it is not
being read as evidence of anything beyond what it states.

## 4. Owner concentration

**32,737 distinct owner addresses hold the 60,049 agents read in this run.**
The largest single owner address holds 2,293 agent ids (3.8% of 60,049).
The next four: 1,608; 1,243; 946; 690. This is reported as a counting fact
about the data — an address holding many agent ids has legitimate
explanations (a single operator running many instances, a factory-pattern
deployer, a marketplace registering on behalf of others) alongside less
legitimate ones, and this run does not distinguish between them. No
clustering or coordination inference is applied; `METHODOLOGY.md` §2 (Rung
7) and §7 both say plainly that this project publishes that kind of
analysis, if ever, in a separately labelled `signals` block, never folded
into a rung or a report table as if it were a measurement of the same kind.

## 5. Caveats

Stated here, before any conclusion, on purpose — a report that discusses its
findings before its blind spots is doing the thing this project exists to
criticize.

- **2,686 of 60,049 agents (4.5%) are rung-2 `error`, not `fail`, and are
  included in every denominator above but pass nothing beyond rung 1.**
  81% of that 4.5% (2,177 agents) is us honoring the origin's own
  `robots.txt` disallow — we did not attempt the fetch because the host
  told us not to, which is different from the host answering and failing.
  The remainder is our own timeouts and robots.txt-fetch failures. None of
  this is scored against the agent; it is called out here because a reader
  who excludes `error` from the denominator gets 31,868 / (31,868 + 25,495)
  = 55.6% resolvable, not the 53.1% in §2 — a different, also defensible,
  number, and the reader should know which one they are looking at and why
  this report's denominator is always all 60,049.
- **`ipfs://` results (2,946 pass, 518 fail, 124 error at rung 2 — 3,588 of
  60,049 agents) depend on one disclosed HTTPS gateway.** A failure
  fetching through that gateway is recorded identically to a failure of the
  agent's own document — this run cannot distinguish "the document is
  unavailable" from "our one gateway had a bad day." No second gateway was
  cross-checked in this run.
- **Rung 6 (`live`) is unmeasured.** Every declared service endpoint's
  actual reachability is untested in this data; the ladder above has a real
  gap between rung 5 and rung 7, not an implicit pass.
- **12 agent ids were discovered but could not be read at all** (an RPC
  failure on our side) and are absent from every number in this report,
  not counted as failing.
- **This is one chain, at one block, at one moment.** Base only, block
  49,230,618 only, one fetch per document. A document that changes an hour
  later, or an endpoint that is mid-deploy when we happened to probe it,
  reads identically to a genuine, lasting problem in this data — we have no
  second read to cross-check against.
