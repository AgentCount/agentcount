## 1. Corrections

This project's first report (`1c87c4f4`, 2026-07-28) is superseded by nine
corrections, applied 2026-07-28 through 2026-07-29. Eight are numbered code
fixes; the ninth is an unnumbered addition (a new rung-5 status,
`unclaimed`) that shipped alongside them. One originates from an external
reviewer. **The other eight are this project's own errors, corrected by its
own re-reading of the spec, its own internal audit, or its own reversal of a
ruling it had made one day earlier** — a corrections section that lists only
someone else's mistakes is not a corrections section.

Before any rerun, applying fixes 1–3 to the *same archived HTTP bodies* from
the first report moved the rung-4 (`conformant`) pass rate **7.0% → 18.5% →
49.2%**, entirely by re-judging evidence already on disk — no new fetch, no
new chain read. That the archive could be re-judged into three materially
different verdicts without touching the network is the archive justifying
its own cost.

1. **FIX 1 — `endpoints` accepted as a legacy alias for `services`
   (2026-07-28, from external review).** The first report failed 25,636
   documents at rung 4; external review flagged that an unknown share
   declare their endpoints under the legacy field name `endpoints` instead
   of `services`. Verified against the spec: the schema block names the
   field `services` (line 62), but the prose never caught up — it still
   says "endpoints" at lines 115, 117, 121, and 402. Of the archived run's
   525 documents that used `endpoints` only, 287 flip from `fail` to `pass`
   under this fix alone (the other 238 were also missing something else).

2. **FIX 2 — `x402Support` and `active` removed from the required set
   (2026-07-28, internal).** The first report failed 6,269 documents at
   rung 4 for lacking `x402Support` alone. Re-reading the spec: both fields
   appear only inside the illustrative example JSON (lines 99–100) and are
   never named by a normative keyword anywhere in the prose. Treating an
   example's keys as mandatory was already strained; it was especially so
   here, since it judged an agent non-conformant for failing to
   affirmatively declare it does *not* support an optional payment
   extension. Combined with FIX 1: **11,107 / 60,049 (18.5%)**, up from the
   original 4,175 / 60,049 (7.0%) — 1.5 points above the work order's own
   pre-fix estimate of ~17%, because the estimate hadn't accounted for the
   359-document overlap between the two fixes.

3. **FIX 3 — rung 4 split by RFC 2119 severity, and Ruling 1 reversed
   (2026-07-29, internal).** The spec invokes RFC 2119/8174 explicitly
   (line 36): MUST, SHOULD, and MAY are different promises, and the
   original rung 4 had compressed all three into one boolean — the exact
   kind of compression this project's own methodology says it exists to
   refuse, committed by this project itself. Re-reading the spec
   field-by-field: the registration file has exactly **one MUST, and it is
   conditional** — `registrations[].agentId` and
   `registrations[].agentRegistry`, checked only when `registrations` is
   present and non-empty (line 123, "all fields in the registration are
   mandatory"). `type`, `name`, `description`, `image`, and `services` all
   move to SHOULD. This required reversing this project's own **Ruling 1**
   (decided 2026-07-27, one day before FIX 1), which had held those four
   fields REQUIRED by reading line 115's SHOULD as governing only their
   *content*, not their *presence* — a reading that did not survive being
   checked against this project's own **Ruling 2**, decided the same day,
   which read the structurally identical line 123 the opposite way. The
   ruling is kept in `spec/REQUIRED_FIELDS.md`, marked reversed, not
   deleted. Re-judged against the same archived bodies: **29,552 / 60,049
   (49.2%)** — up from 18.5%. 259 documents (0.9% of those reaching rung 4)
   still failed in that archived re-judgement, every one for a missing
   `agentId` and/or `agentRegistry` inside a present `registrations` entry —
   the only way to fail rung 4 under this fix.

4. **FIX 4 — rung 7 ungated from rungs 1–5 to rung 1 alone (2026-07-29,
   internal).** Reputation feedback lives in the Reputation Registry, keyed
   by agent id, and is readable regardless of whether that agent's document
   ever resolved, parsed, conformed, or bound — the old gating (rungs 1
   through 5 must all pass first) was an accident of implementation
   history, not a real dependency. Ships with FIX 5 in the same run, because
   ungating without also fixing the framing below would have published a
   tautological finding at ~60,000-agent scale instead of ~1,437 — worse,
   not better.

5. **FIX 5 — rung 7 renamed `independent` → `attested`; self-review framing
   dropped (2026-07-29, internal — this project's own prior finding
   retracted).** The pinned spec is explicit — line 217: *"The feedback
   submitter MUST NOT be the agent owner or an approved operator for
   `agentId`."* Owner self-feedback cannot be successfully submitted; it is
   a contract-level invariant, not something a check can catch in the wild.
   The old `independent` rung compared feedback authors against the owner
   anyway and reported "zero agents caught writing their own reviews" in the
   first report — restating a rule nobody can break is not a finding, and
   publishing it at full population scale would have been publicly
   corrected within a day. The two evidence fields that carried that
   comparison (`authors_equal_to_owner`, `self_feedback_ratio`) are removed
   from the rung entirely, not renamed. **This retraction, and the fact
   that this rung does not and cannot detect self-review, is stated here
   because it is a correction to the first report — the rung's substantive
   findings are out of scope for this report; see the scope note above.**

6. **NEW — rung 5 gains a fifth status, `unclaimed` (2026-07-29, internal).**
   Once FIX 3 made `registrations` a SHOULD, a document can pass rung 4
   while declaring zero registrations, and rung 5 ("does this document name
   the on-chain record it was fetched from") has nothing to check for it.
   None of the four original statuses was honest: `pass` would claim a
   verification that never happened, `fail` would punish a merely
   recommended field as hard as an outright wrong claim, `skipped` would
   falsely imply rung 4 failed, `error` would falsely imply this checker
   malfunctioned. Re-judged against the archived run: pass count rose
   1,437 → 4,055 even as the pass *rate* fell 34.4% → 13.7%, because the new
   rung-4-pass population is 83.6% documents that never made a registration
   claim at all. See Section 4 for this run's own figures.

7. **FIX 6 — `absent` vs `skipped` distinguished for rungs 4 and 5
   (2026-07-29, internal — found in this project's own pre-publication
   audit, not from the external review).** The sweeper only constructed
   rung 4 and rung 5 rows when rung 3 had actually handed back a parsed
   document; when there was nothing to parse, no row was written at all —
   indistinguishable from rung 6, which genuinely isn't implemented. In the
   archived run this affected **29,985 agents** that had no rung-4/5 row of
   any kind: 25,242 from a rung-2 `fail`, 2,686 from a rung-2 `error` (ours,
   not the agent's), and 2,057 where rung 2 passed but rung 3 itself failed
   or errored — a case the original work order's "failing rung 2" framing
   didn't even name. Fixed so rungs 4 and 5 are always constructed and
   always land on `skipped` (naming the actual blocking rung) rather than
   producing no row.

8. **FIX 7 — `data:` URI decoding gains five fallback paths, including gzip
   (2026-07-29, internal, measured before implementing).** The ecosystem's
   documented convention is
   `data:application/json;enc=<algorithm>[;level=<n>];base64,<payload>`.
   Queried the archived population before writing any decoding code: 399
   documents declare `enc=`, and **all 399 declare `gzip`** — zero declare
   `zstd`, `brotli`, or `lz4`. Only `gzip` — the one algorithm the
   population actually uses — got a real dependency added. This run:
   **399 documents decode via `enc=gzip`, zero via any other declared
   algorithm** (confirmed again below, not carried over from the archived
   count). A `data:` URI declaring an algorithm this parser doesn't
   implement is `error`, not `fail` — we understood what was declared, we
   simply can't decode it.

9. **FIX 8 — IPFS fetches try three gateways in sequence, reversing this
   project's own ruling from the day before (2026-07-29, internal).** The
   2026-07-28 ruling deliberately used one disclosed gateway (`ipfs.io`) so
   a failure would be honestly attributable to the agent, not to us. That
   ruling's own goal collapsed in practice: a single gateway's outage became
   indistinguishable from an agent's content being genuinely unpinned,
   which is exactly the ambiguity the one-gateway choice was meant to avoid.
   `https://ipfs.io/ipfs/`, `https://cloudflare-ipfs.com/ipfs/`, and
   `https://gateway.pinata.cloud/ipfs/` are now tried in order; all three
   failing is still `error`, never `fail`, for the same reason as before —
   we cannot distinguish an unpinned CID from a gap in what our three chosen
   gateways happen to cache.

## 4. Rung 5 (`bound`) — lead with `unclaimed`

**84.6% of documents that pass conformance (25,182 / 29,778) make no
binding claim at all.** `unclaimed` means the document carries no
`registrations` array — or an empty one — for rung 5 to check; there is
nothing to have matched or mismatched, because nothing was claimed.

The spec's own Security Considerations state (`spec/ERC8004SPEC.md`, line
428):

> "While this ERC cryptographically ensures the registration file
> corresponds to the on-chain agent, it cannot cryptographically guarantee
> that advertised capabilities are functional and non-malicious."

For the great majority of documents that pass rung 4 — 84.6% of them —
**there is nothing to cryptographically ensure**, because the document
never made the claim that rung 5 (and the spec's own security language)
presupposes it would make. This is a direct consequence of FIX 3: once
`registrations` moved from an implied requirement to SHOULD, a document
could pass conformance while opting out of the one claim the spec's
security framing depends on.

The remaining, smaller finding: of the 4,596 documents that did make a
registration claim (3,807 + 789 = 4,596 of 29,778, i.e. those not
`unclaimed`), **789 (17.2% of claims made, 2.65% of all rung-4 passes)**
claim a chain, registry, or agent id that does not match the one this
document was actually fetched from** — an affirmative wrong claim, not an
omission. 3,807 (82.8% of claims made) match. See `spec/REQUIRED_FIELDS.md`
Ruling 2 for why the array's presence is SHOULD while its contents, when
present, remain mandatory.

## 5. Rung 4 (`conformant`) — the SHOULD distribution, not the boolean

**The near-vacuous binary is the finding.** Under an honest RFC 2119
reading, the registration file has exactly one MUST, and it is conditional:
`registrations[].agentId` and `registrations[].agentRegistry`, checked only
when a `registrations` array is present and non-empty. Every other field
this rung once treated as unconditionally required — `type`, `name`,
`description`, `image`, `services` — is SHOULD (spec line 115); `x402Support`,
`active`, and `supportedTrust` are MAY. That is why 99.2% of documents that
reach rung 4 pass it (29,778 / 30,031): **ERC-8004 imposes almost no
unconditional requirement on this document**, and the 49.5%/99.2% figures
above describe that fact, not an achievement of the registered population.
This is reported as measured; it is not dressed up as either a scandal or a
success.

The interesting number moves to the **SHOULD-completeness distribution** —
how many of the seven SHOULD checks a document actually satisfies, of the
30,031 documents that reach rung 4:

| SHOULD gaps | Documents | % of 30,031 |
|---:|---:|---:|
| 0 | 897 | 3.0% |
| 1 | 3,086 | 10.3% |
| 2 | 12,702 | 42.3% |
| 3 | 3,140 | 10.5% |
| 4 | 10,151 | 33.8% |
| 5 | 40 | 0.1% |
| 6 | 15 | 0.0% |

Only **897 documents (3.0%)** satisfy all seven SHOULD checks. The
distribution is bimodal — clustering at 2 and 4 gaps — not a smooth quality
gradient; Section 6 tests, and largely rejects, one candidate explanation
for that shape.

**Most common SHOULD gaps**, of the same 30,031 (a document can, and
usually does, contribute to several rows):

| Gap | Documents | % of 30,031 |
|---|---:|---:|
| `registrations` (absent or empty) | 25,182 | 83.8% |
| `type` | 15,828 | 52.7% |
| `services` (absent) | 13,146 | 43.8% |
| `image` | 12,493 | 41.6% |
| `services[].version` (≥1 entry) | 6,878 | 22.9% |
| `services_empty` (present, zero entries) | 5,181 | 17.3% |
| `description` | 76 | 0.3% |
| `name` | 20 | 0.1% |

`description` and `name` are supplied almost universally (99.7% and 99.9%
of documents), while `type` and `image` are each missing on roughly half the
population — the four fields this project's own superseded Ruling 1 once
treated as one unit behave nothing alike in practice.

**`services_status` — the share declaring no reachable service at all**:
absent 13,146 (43.8%), empty 5,181 (17.3%), present and non-empty 11,704
(39.0%). **61.0% of documents that otherwise parse as a valid agent
registration file (18,327 / 30,031) declare no way to reach the agent at
all**, whether by omitting the field entirely or supplying it empty.

> The work order called zstd the recommended compression. The population
> says otherwise: 399 documents use gzip and **zero** use zstd, brotli or
> lz4. Three dependencies were not added because someone counted first.

(Verified fresh against this run: of 3,590 `ipfs://`-scheme agents, 2,993
resolve via the three-gateway fallback and 597 exhaust all three gateways —
recorded `error`, not `fail`, per FIX 8. Of 15,458 `data:`-scheme documents
carrying a base64 payload, 399 declare `enc=gzip` and decode; zero declare
any other compression algorithm; `unsupported_compression` accounts for
zero rung-2 results in this run.)

## 6. Investigation A — a hypothesis tested and rejected

**The template/batch-minter hypothesis was tested against owner
concentration and rejected.** The candidate explanation for the 4-gap peak
above (10,151 documents, 33.8%) was that a small number of registrants —
sybil-style batch minting, or one dominant tool run by one operator — could
account for most of it. Recomputed against this run's own evidence
(matching `analysis/should-gap-signatures.md`'s method, originally run
against the archived pre-rerun evidence; re-run here against the current
reference run to confirm the conclusion still holds):

- The single dominant SHOULD-gap signature — missing exactly `image`,
  `registrations`, `services`, and `type` while keeping `name` and
  `description` — accounts for **10,101 documents, 33.6% of the 30,031 that
  reach rung 4**, and **99.5% of the entire 4-gap peak**.
- That signature is used by **6,460 distinct owners**, at **1.56 documents
  per owner** — statistically indistinguishable from the population
  baseline of **1.61 documents per owner** across 18,617 distinct owners.
  The largest single owner using this exact signature accounts for only
  **22.7%** of it.
- 41 distinct SHOULD-gap signatures exist across the whole 30,031-document
  population.

**A hypothesis this project's author wanted — that the bimodal distribution
traces to a small number of bad actors — was tested and refused by the
data.** The dominant pattern reads as a widely-shared registration default
(plausibly one SDK, template, or tutorial whose minimal example sets `name`
and `description` but not the other four fields), adopted independently by
thousands of unrelated registrants, not the output of one entity. A smaller
number of signatures (four of the top twenty, collectively ~11% of the
population in the original analysis) do show genuine single-owner
concentration (47–92% from one address) — that pattern exists, but it is a
minority contributor, not the explanation for the bulk of the distribution.

That the SHOULD gaps are broadly-shared tooling defaults, not a handful of
bad actors, means these numbers describe the ecosystem's actual practice
rather than a few outliers — which makes the census harder to dismiss, not
easier.

## 7. Investigation B — the 253 remaining rung-4 failures

253 documents fail rung 4 in this run — every one for a `registrations`
entry missing `agentId` and/or `agentRegistry`, the only way to fail this
rung under the current spec reading. (This is a different figure from the
259 reported in `analysis/should-gap-signatures.md`, which was computed
against the archived pre-rerun run `1c87c4f4`; the population shifted once
this run applied FIXES 7 and 8 — gzip decoding and the IPFS gateway
fallback — which changed which documents reach rung 3/4 at all. 253 is the
number for this reference run, recomputed directly against it, and is what
the rest of this section describes.)

**The concrete cluster: 48 agents, 48 distinct owners, one named
third-party host, one identical defect.** Every agent whose `tokenURI`
resolves to `https://api.orbit-agents.com` — 48 of them, from **48
different owner addresses**, no owner holding more than one — fails rung 4
for the *same* missing field: `agentRegistry`, never `agentId`. This is a
service-level bug in one third-party agent-hosting platform, affecting 48
unrelated registrants who have no reason to know their generated documents
are non-conformant. It accounts for 48 of the 56 agents (85.7%) whose only
missing field is `agentRegistry`. **This is named, fixable, and upstream of
any individual registrant** — the most actionable single fact this census
produced, and worth notifying the host directly rather than only publishing.

The remaining 205 failures:

- **One large single-owner cluster: 54 agents, one owner
  (`0xd3d03f57c60bbefe645cd6bb14f1ce2c1915e898`), one platform.** Every
  document's `image` and service endpoints point at `automaton.cloud`;
  every one supplies `agentRegistry` correctly but leaves
  `registrations[0].agentId: null`. Sampled names are self-evidently test
  fixtures — `TestBot`, `OnChainTestBot`, `FullFlowTestAgent`, `Research
  Agent` (reused verbatim across different agents) — consistent with one
  hosting/deployment tool generating demo agents whose template fills
  `agentRegistry` but not `agentId`, which the tool cannot know until after
  the mint that creates it.
- **A tail of smaller multi-agent operators:** 12 owners with 2–11 failing
  agents each, 57 agents total (22.5% of 253).
- **A genuinely independent remainder:** 94 owners with exactly one failing
  agent each, on hosts and document shapes that vary — a real long tail of
  independent implementation mistakes (the same easy-to-miss requirement,
  an `agentId` that cannot be known until after the mint that produces it),
  not one shared tool.

Missing-field breakdown across all 253: `agentId` only, 180 (71.1%);
`agentRegistry` only, 56 (22.1%); both, 17 (6.7%). `agentId`-missing
dominates, consistent with tooling that knows its own registry address at
generation time but not its freshly-minted token id.

**Not one broken tool, and not entirely independent errors either** — 102
of 253 (40.3%) trace to the two identified clusters above (one operator, one
platform bug), the rest split between a tail of small multi-agent operators
and a genuinely independent long tail.

## 8. Rung 7 (`attested`) — 49.2%, and what that number does not cover

**29,570 of 60,097 agents (49.2%) pass rung 7: at least one address has left
that agent a Reputation Registry feedback entry. That is the entire claim
this rung supports, and it is narrower than the headline number suggests.**
Rung 7 counts agents *reached*, not reviewers who reached them, and by
construction it cannot tell one address that fed 10,000 agents apart from
10,000 independent authors who each left one review — both produce the same
`pass`. This was investigated before publication, because a rung that moved
from a ~1,437-agent denominator to a ~60,000-agent one under FIX 4 deserved
scrutiny of what its new headline actually means, not just its count. The
investigation is `analysis/attestation-rate.md`; this section reports what
it found.

**The stored, population-wide distributions are heavily skewed, not flat.**
Among all 29,570 attested agents, queried directly against this run's
`check_results` (rung 7, `status = 'pass'`):

- `feedback_count`: median **2**, mean 4.86, p90 10, p99 21, max **12,129**
  (one agent, id 55985).
- `distinct_authors`: median **1**, mean 2.25, max **8,754**.
- **53.4% of attested agents (15,806 / 29,570) pass on the strength of a
  single client address**, and 36.6% (10,817) have exactly one feedback
  entry from exactly one author — the minimum possible way to clear this
  rung. The median attested agent was vouched for by one address, once or
  twice.

Stored evidence records counts, not the client addresses themselves, so
whether the same handful of addresses recur across thousands of agents
cannot be answered from `check_results` alone — that question was put to a
live sample of the chain instead.

**Sampling discipline.** 300 agents — about 1.0% of the 29,570-agent
attested population — were drawn with `setseed(0.42)` and `order by random()`
inside a single Postgres session, then each read live via `getClients` on
the Reputation Registry, pinned to this run's own block, **49,262,617** — the
same block every other on-chain read in this report used, so the sample
describes the exact state this run judged, not a later one. All 300 reads
succeeded (zero failures, no exhausted retries), and all 300 were checked
against this run's own stored `distinct_authors` for the same agent: **0
mismatches**. That distinction matters — the distributions above are a
full-population fact from stored data; everything below is what a 1% sample
suggests, carrying a sampling error the stored figures do not.

- One address, `0xf653…807e`, appears as a feedback author for **143 of the
  300 sampled agents (47.7%)** — Wilson 95% CI **42.1–53.3%**, i.e. an
  estimated **12,400–15,800** of the 29,570 attested agents.
- Widening to the **top 6 addresses: 274 of 300 sampled agents (91.3%, 95%
  CI 87.6–94.0%)** have at least one of those six among their authors, and
  **263 of 300 (87.7%, 95% CI 83.5–90.9%)** have *every* feedback entry
  traceable to those same six and no other author at all.
- n=300 is a sample, not a census of authorship, drawn once with a single
  fixed seed and not repeated with independent draws — the confidence
  intervals above are the honest uncertainty band on this finding, not a
  point fact the way the stored-data figures above are.

**Attestation is mildly anti-correlated with document quality — the most
counterintuitive fact here.** Joining rung 7 against rung 2 (`resolvable`)
for this run: 46.8% of attested agents (13,832 / 29,570) have a resolvable
document, versus 58.6% of non-attested agents (17,875 / 30,527) — confirmed
directly against `check_results` for this run. **53.2% of attested agents
(15,738 / 29,570) have no resolvable document at all** (rung-2 `fail` or
`error`) yet still carry Reputation Registry feedback. An agent that never
resolves, parses, or conforms to the spec at all can still pick up feedback
from the registry; agents with feedback are, if anything, *less* likely to
serve a working document than agents without it, not more.

Ownership is not where the concentration sits: 15,698 distinct owners hold
at least one attested agent, and the 10 owners with the most attested agents
account for only **10.5% (3,111 / 29,570)** of the whole attested
population — no small set of *owners* dominates. But the *conditional*
attestation rate swings enormously by owner: some owners holding 1,000+
agents show essentially 0% attested, while other similarly-sized owners
clear 50–95%+. Which owner an agent belongs to strongly predicts whether it
clears rung 7; a small number of *owners* dominating the count does not.

**Rung 7 as defined cannot distinguish one reviewer from many, and that is a
limitation of the check, discovered by investigating its own result — said
here plainly rather than left for a reader to find.** The check is correct
for what it claims: `pass` means "at least one address left this agent
feedback," and every one of the 29,570 agents counted here satisfies exactly
that. The claim a reader is likely to attach to 49.2% — "half of registered
agents received independent attention from the ecosystem" — is not what was
measured, and the concentration evidence above is why the gap between those
two readings is not a hypothetical caveat in this population.

*Footnote on a ~6% figure raised during this project's own planning.* A
source has since been found: Mafrur & Khusumanegara, "From Agent Identity to
Agent Economy," arXiv:2606.12128 (10 June 2026), analysed 10,000 Ethereum
ERC-8004 agents and found 628 had received reputation feedback — **6.3%**
(companion dataset: arXiv:2604.22652). That resolves the sourcing problem
noted in earlier drafts of this report, but it does not make the number
comparable to 49.2%, and this report does not present it as a comparison.
Four differences stand between the two figures: a different chain (Ethereum,
not Base), materially different gas economics between the two chains, a
sample drawn roughly six weeks before this run's 2026-07-29 pin, and no way
to tell from the paper whether their 628 came from a live registry read
(this report's rung 7 equivalent, `getClients`) or from indexed feedback
events — two different quantities that need not agree even on the same
chain. Noted here as context on the same phenomenon in a neighboring
population, not as a headline ratio.

**Verdict: concentrated activity, not broad adoption.** 29,570 (49.2%) is a
real, reproducible count of agents with at least one Reputation Registry
feedback entry — that part of the finding stands without qualification. But
six client addresses, not 29,570 independent reviewers, account for the
overwhelming majority of what this rung counts as `attested`, and the same
population is, if anything, slightly less likely to have a working document
than the population that failed this rung. Read 49.2% as "reached by a
concentrated set of active reputation-system participants," not as "broadly
and independently reviewed."

## 9. Caveats

Stated before any conclusion is drawn from them, not appended after —
inline within each section above where they apply, and collected here so
none is missed.

- **3,026 of 60,097 agents (5.0%) are rung-2 `error`, not `fail`,** and are
  included in every denominator above but pass nothing beyond rung 1. 2,182
  of those (72.1%) are us honoring the origin's own `robots.txt` disallow —
  we did not attempt the fetch because the host told us not to. 597 more
  are the IPFS three-gateway fallback exhausting all three (FIX 8); the
  remainder is our own timeouts and robots.txt-fetch failures. None of this
  is scored against the agent.
- **`ipfs://` results (2,993 pass, 597 error at rung 2 — 3,590 of 60,097
  agents, 6.0%) depend on three gateways answering, tried in sequence
  (FIX 8).** All three failing is recorded as `error`, never `fail` — we
  cannot distinguish an unpinned CID from a gap in what these three
  gateways happen to cache.
- **`data:` URIs declaring a compression algorithm this parser does not
  implement are `error`, not `fail`** (FIX 7). Zero occurred in this run —
  every `enc=` declaration observed (399) is `gzip`, which is implemented —
  but the classification exists and would apply if a future run encountered
  `zstd`, `brotli`, or `lz4`.
- **Rung 6 (`live`) is unmeasured.** Every declared service endpoint's
  actual reachability is untested in this data; the ladder has a real gap
  at rung 6, not an implicit pass.
- **Rung 7's 49.2% measures reach, not independent review, and cannot tell
  the two apart by construction.** The full 29,570-agent stored population
  shows heavy skew (median 2 feedback entries, median 1 distinct author);
  a 300-agent live sample (~1.0% of that population, pinned to this run's
  own block, all 300 validated against stored evidence) found 6 addresses
  behind an estimated 84–91% of the attested population. Treat the
  concentration figures as sample-derived estimates with the stated
  confidence intervals, not as census facts the way the pass/fail counts
  are — see Section 8.
- **1 agent id was discovered but could not be read at all** (an RPC
  failure on our side) and is absent from every number in this report, not
  counted as failing.
- **This is one chain, at one block, at one moment.** Base only, block
  49,262,617 only, one fetch per document. A document that changes an hour
  later, or an endpoint mid-deploy when we happened to probe it, reads
  identically to a genuine, lasting problem in this data.
- **A passing ladder is not an endorsement**, and a failing rung is a dated
  observation about a document, not a claim about the team behind it. See
  `METHODOLOGY.md` §7 for the full statement of what this data does not
  claim.

## 10. Owner concentration

**32,745 distinct owner addresses hold the 60,097 agents read in this
run.** The largest single owner holds 2,293 agent ids (3.8% of 60,097). The
next four: 1,613; 1,243; 968; 690. This is reported as a counting fact — an
address holding many agent ids has legitimate explanations (one operator
running many instances, a factory-pattern deployer, a marketplace
registering on behalf of others) alongside less legitimate ones, and this
run does not distinguish between them. No clustering or coordination
inference is applied beyond what Sections 6 and 7 report explicitly as
investigations, not rungs.
